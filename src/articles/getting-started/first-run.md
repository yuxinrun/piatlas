## 技术背景

usage.md 说明 Pi 使用当前目录发现文件、说明、配置，并按目录分组保存会话。也就是说，你从哪里启动 Pi，本身就是一次上下文选择。
交互界面包含 transcript、编辑器、工具调用与结果、footer 状态区。首次运行的目标不是“让它写代码”，而是看清证据从哪里进入会话。

## 核心原理

首次运行应按“观察—解释—验证”三步走：先让 Pi 描述目录，再要求它解释判断依据，最后用 ! 命令核对。这样能把模型叙述与工具事实区分开。
如果回答与工具输出不一致，应该修正提示或会话状态，而不是默认模型拥有隐藏的文件访问能力。

## 核心代码解释

```bash
cd /path/to/safe-sandbox
pi

# 在 Pi 编辑器中输入
这个目录里有哪些文件？请只根据工具结果回答。

!git status

# 结束后
/name first-readonly-run
/exit
```

!git status 会把输出加入对话；usage.md 还说明 !! 命令的输出不会发送给模型。此例只用只读命令。

## 实际执行过程

1. 进入不含敏感数据的临时目录，启动 pi。
2. 发送只读问题，观察工具调用与结果区域。
3. 用 ! 命令核对输出，再让 Pi 根据证据修正回答。
4. 用 /session 查看会话信息，记录路径与消息数。
5. 退出后用 pi --continue 恢复会话。

## 设计优点与局限

- 优点：交互式反馈密集，适合建立机制直觉；会话按目录组织便于复盘。
- 局限：信息量较大，新手容易把工具输出和模型解释混在一起。

## 容易出现的问题

- 在真实生产仓库第一次就运行写入任务。
- 忽略项目信任提示，直接加载项目扩展。
- 把 /export 导出的 JSONL 当作完整会话树的唯一真相。

## 实战案例

创建三个不同扩展名的文件，让 Pi 统计数量；要求它先列出证据，再给结论。对照文件系统检查。

## 最佳实践

首次会话使用 /name 命名；把成功和失败的提示词都保留下来，作为后续自动化模板。

## 常见问题

### 退出后如何继续？

usage.md 确认 pi --continue 会恢复同一目录最近一次会话。

### 如何查看会话状态？

使用 /session；文档说明它可查看文件、ID、消息数、token 用量和费用。
