## 技术背景

README 给出两类安装路径：官方安装脚本，以及 npm 全局安装。二者差异不在“能不能跑”，而在传递依赖是否锁定。官方明确说安装脚本会从 install-lock 安装以固定传递依赖，而 npm 方式不固定传递依赖。
固定快照的根 package.json 要求 Node >=22.19.0。安装前先核对运行时，比事后排查 “语法不支持” 更高效。

## 核心原理

安装 Pi 本质是把 CLI 包和一组库放进可运行环境。真正需要管理的不是“一个二进制”，而是三层版本：Node 运行时、Pi 包版本、Provider 凭据与模型配置。
Pi 的默认执行权限等于启动用户权限，因此安装位置本身不是安全边界。安全边界应在容器、用户权限和工作目录层面建立。

## 核心代码解释

```bash
# 官方快照给出的安装命令（执行前请先审阅脚本来源）
curl -fsSL https://pi.dev/install.sh | sh

# Windows
powershell -c "irm https://pi.dev/install.ps1 | iex"

# npm 方式：注意官方说明它不固定传递依赖
npm install -g --ignore-scripts @earendil-works/pi-coding-agent

node --version
pi --version
```

本文不执行任何安装命令。生产或团队环境建议先下载脚本审阅，再决定是否运行；npm 的 --ignore-scripts 来自官方说明。

## 实际执行过程

1. 先运行 node --version，确认满足 22.19.0 或更高版本。
2. 选择一个隔离目录，按官方方式安装并记录 pi --version。
3. 运行 pi，进入交互界面后立刻用只读命令验证，不做文件写入。
4. 在文档中记录你选择的安装方式，方便日后复现。

## 设计优点与局限

- 优点：官方安装路径给出固定依赖；npm 路径更贴近常规 Node 工具链。
- 局限：管道式安装脚本需要额外审阅；npm 路径不固定传递依赖。

## 容易出现的问题

- 在全局安装后直接在敏感仓库中测试写操作。
- 把 Node 版本忽略，导致构建与运行行为不一致。
- 用同一个用户同时保存生产凭据和测试凭据。

## 实战案例

建立 /tmp/piatlas-install-check 之类的临时目录，安装后只运行只读命令，并保存终端输出作为环境核验记录。

## 最佳实践

把安装命令、Node 版本、Pi 版本写入团队的环境说明；升级前先复制一份可回滚配置。

## 常见问题

### 必须用安装脚本吗？

不是。README 同时给出 npm 与 Nix 路径；差异主要是依赖锁定方式。

### 安装后为什么还要沙箱？

因为 Pi 默认继承启动用户权限，安装方式本身不改变这个边界。
