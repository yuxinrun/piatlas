## 技术背景

官方 usage 文档明确列出 /login 与 /logout 管理 provider 登录；README 也说明可用内置 AI provider 通过 /login 连接订阅或 API key。除这些已核验入口外，本文不声称某个环境变量名一定有效。
固定快照的 coding-agent 公开入口包含 readStoredCredential 与 ModelRegistry，说明凭据处理由 CLI 层负责，而不是由模型层自行读取。

## 核心原理

凭据配置的目标不是“让它能跑”，而是“让需要的地方刚好能用”。对 Pi 来说，进程、扩展、内置工具与用户命令处于同一信任上下文；任何能执行代码的组件都可能读到该进程可见的凭据。
因此凭据边界要和隔离边界一起设计：完整 Pi 进程隔离时，凭据进入该进程；工具级隔离时，宿主机进程仍可能看到凭据。

## 实际执行过程

1. 在隔离目录启动 pi，执行 /login 并按 Provider 提示完成配置。
2. 运行一个只读提示，确认模型请求成功。
3. 检查终端日志、会话导出和 shell history，确认没有明文凭据。
4. 在另一台机器上重复，验证配置的可迁移性。

## 设计优点与局限

- 优点：交互式登录减少手工复制密钥；凭据处理集中在 CLI 层。
- 局限：进程内扩展与工具可能读取同一环境中的凭据；容器方案需额外设计。

## 容易出现的问题

- 把 API Key 写进项目 .env 后又用 /share 分享会话。
- 在容器内挂载宿主机 ~/.pi/agent，意外带入全部凭据。
- 为测试和生产使用同一个密钥，导致轮换困难。

## 实战案例

建立两组凭据：一组用于本地只读实验，一组用于正式任务。每次实验后轮换或撤销不再使用的测试凭据。

## 最佳实践

先用 /login 完成最小配置；再阅读 containerization 文档选择隔离方案；最后把“哪些组件可见凭据”写进团队风险清单。

## 常见问题

### Pi 会替我限制凭据访问吗？

不会。README 明确说 Pi 不内置这类权限系统。

### 本文为什么不给具体环境变量名？

因为已核验文档没有统一承诺某个变量名；避免把 Provider 约定误写成 Pi API。
