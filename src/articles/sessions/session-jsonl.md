## 技术背景

how-pi-works.md 明确说明持久化会话是 JSONL 文件，每个树条目都有 ID 并指向父条目，当前条目标识活动分支。coding-agent 的公开入口包含 SessionManager、parseSessionEntries、buildSessionContext、CURRENT_SESSION_VERSION 等导出。
这说明“文件里的记录”与“发给模型的上下文”不是同一个东西：前者是完整树，后者是活动分支的投影。

## 核心原理

JSONL 的优势是追加友好：一次事件写入一行，不必重写整棵会话树。读取端再按 id/parent 构建索引，找到当前叶子并回溯出上下文。
因此恢复会话时要保持三个概念分离：存储条目、树结构、模型消息投影。直接把文件全文塞给模型会破坏分支语义。

## 核心代码解释

```json
// 教学用 JSONL 文本；不是 Pi 的真实字段全集
{"id":"e0","parentId":null,"type":"user","text":"开始"}
{"id":"e1","parentId":"e0","type":"assistant","text":"调用工具"}
{"id":"e2","parentId":"e1","type":"toolResult","text":"ok"}
{"id":"e3","parentId":"e1","type":"user","text":"换一种方法"}

// 读取原则：
// 1. 逐行解析；2. 建 id 索引；3. 从 current leaf 回溯；4. 再转成模型消息。
```

真实 SessionManager 还处理迁移、版本与压缩条目；本例只演示父引用与投影的关系。

## 实际执行过程

1. 导出一个会话为 JSONL，观察每行是否独立解析。
2. 找出 id 与 parent 字段，画出父子关系。
3. 选择不同叶子，手工写出两条祖先链。
4. 检查上下文投影是否只包含所选路径。

## 设计优点与局限

- 优点：追加写入简单；分支与审计信息天然保留。
- 局限：手工解析容易遗漏版本迁移；树结构需要额外索引。

## 容易出现的问题

- 把 JSONL 行数当成消息数。
- 按行顺序当作唯一历史，忽略 parent。
- 导出含敏感正文的会话后直接分享。

## 实战案例

任务：写一个 20 行脚本，输入 id 与 parent，输出从根到叶的标题链。然后故意制造一个环，确认程序不会死循环。

## 最佳实践

解析失败时保留原始行；对未知条目类型显式告警；分享前脱敏。

## 常见问题

### JSONL 是会话真相吗？

它是持久化真相之一；模型上下文是按活动分支重建的投影。

### 能否手动编辑会话？

可以实验，但应先复制文件，并确认版本字段与迁移规则。
